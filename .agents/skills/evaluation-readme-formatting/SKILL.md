# Evaluation README Formatting

Use this skill to turn research evaluation notes into readable Markdown README files. Focus on organization and clarity. Do not change experiment logic, commands, metrics, or result interpretation beyond what is supported by the source text.

## Required Structure

Write the Markdown in this order:

1. タイトル
2. 評価の要約
3. RQ
4. 評価指標
5. 入力と出力
6. 結果の読み方
7. 実行手順
8. 比較対象
9. 処理手順の内部仕様
10. パラメータ
11. 注意点

Use these exact second-level headings where possible:

```markdown
# 評価N: ...

## 評価の要約
## RQ
## 評価指標
## 入力と出力
## 結果の読み方
## 実行手順
## 比較対象
## 処理手順の内部仕様
## パラメータ
## 注意点
```

Do not add a section named `この評価で見ないこと`.

## Writing Rules

- Place `結果の読み方` immediately after `入力と出力`.
- Use tables for metrics, inputs, outputs, comparison targets, parameters, and output-file interpretation.
- Wrap file paths, column names, parameter names, command options, and script names in backticks.
- Preserve existing experimental conditions and results. Do not invent new thresholds, paths, datasets, result values, or claims.
- Remove redundant prose. Keep the tone natural for a research memo.
- When the user requests Markdown body only, output only Markdown without preface or explanation.
- If editing repo files, update only the requested docs unless the user explicitly asks for broader changes.

## Execution Steps

In `## 実行手順`, do not use a single summary table as the main procedure. Use numbered step headings, and put each command directly inside its corresponding Step.

Use this form:

~~~markdown
### 1. 🟨 **条件付き** 代表状態系列CSVを作成する

`results/.../state_series.csv` がなければ実行する。既に同じ条件で作成済みならスキップしてよい。

```bash
uv run python scripts/...
```
~~~

Allowed Step labels:

| ラベル | 意味 |
|---|---|
| 🟥 **必須** | 評価を実行するために必ず行う |
| 🟨 **条件付き** | 対応する出力ファイルがなければ実行する |
| 🟩 **スキップ可** | 比較対象から外す場合やコード変更がない場合は実行しなくてよい |

Execution-step rules:

- Make execution order explicit with `### 1. ...`, `### 2. ...`.
- Put the execution condition and corresponding command in the same Step.
- Do not separate a procedure table from later command blocks.
- Do not include checking commands such as `ls`.
- Mark the main evaluation command as 🟥 **必須**.
- If an intermediate file such as `results/.../state_series.csv` is needed only when missing, mark it as 🟨 **条件付き**.
- If an optional comparison such as FP-Growth can be omitted, write the omission or alternate command as a separate 🟩 **スキップ可** Step.
- If a baseline is automatically generated by the evaluation script and has no separate command, do not make it an independent Step. Explain it inside the evaluation Step.

## Result Reading Pattern

In `## 結果の読み方`, describe files in this order:

1. First summary file to inspect, such as `evaluation*_summary*.csv` or `evaluation_summary.json`.
2. Detail file to inspect next, such as `*_details.csv` or pattern-level output.
3. Reproduction-condition file to inspect last, usually a summary JSON or config-backed output.

Prefer a table with:

| ファイル | 書かれている内容 | 注目する点 |
|---|---|---|

## Safety Checks

Before finishing, check the edited Markdown for:

- Required headings are present and in the requested order.
- No `この評価で見ないこと` section exists.
- No `ls` or similar confirmation-only command is included.
- `## 実行手順` uses numbered `###` Step headings.
- Each command belongs to a specific Step.
- Paths, columns, and options use backticks.
- No unsupported experiment condition or result has been added.
